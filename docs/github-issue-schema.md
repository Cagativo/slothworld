# GitHub Issue Schema (Slothworld)

This document defines the strict structure for all GitHub issues generated by AI.

---

# 📦 Standard Issue Format

Every issue MUST follow:

---

## Title

* Clear, atomic, action-based
* Represents one unit of work

---

## Description

Must include:

* Context
* Why this is needed
* System area affected (Engine / Worker / UI / Selector / Bridge)

---

## Acceptance Criteria

Must be deterministic and testable:

Example:

* [ ] TaskEngine processes event correctly
* [ ] No lifecycle mutation outside TaskEngine
* [ ] Selector output remains deterministic
* [ ] UI consumes only selector outputs

---

## Dependencies

* List prerequisite issues or system components

---

## Affected Modules

Must explicitly list:

* engine
* workers
* selectors
* ui
* bridge-server
* providers

---

# 🤖 Copilot Execution Instructions (REQUIRED)

This section defines how the AI worker executes the task.

## Goal

* 1–2 sentence description of the exact outcome

## Scope

* Allowed files to modify: <explicit paths>
* Forbidden: any file not listed

## Steps

* Ordered, concrete changes only
* No high-level descriptions

Example:

1. Remove STRICT-mode throws in validate()
2. Ensure function returns { valid, errors }

## Constraints

* Do NOT modify tests
* Do NOT introduce new dependencies
* Preserve existing APIs and function signatures
* Keep changes minimal and localized

## Definition of Done

* `npm test` passes
* No new lint errors
* Acceptance criteria satisfied

## Output

* Must return a minimal diff only
* No explanations

---

# 🧠 Issue Types

## 1. Engine Issue

* TaskEngine or lifecycle changes

## 2. Worker Issue

* execution logic changes

## 3. UI Issue

* selector-based rendering changes

## 4. Selector Issue

* derived state changes

## 5. Infrastructure Issue

* CI, workflows, enforcement systems

---

# 📏 Atomicity Rule

Each issue MUST:

* represent exactly ONE unit of execution work
* be independently implementable
* not mix UI + engine + worker logic

---

# ⚠️ Lifecycle Safety Rule

No issue may:

* mutate lifecycle state outside TaskEngine
* bypass ACK mechanism
* introduce non-deterministic state transitions

---

# 🚫 Forbidden Patterns

Issues MUST NOT:

* contain vague tasks (“improve system”, “refactor engine”)
* mix multiple system layers
* skip acceptance criteria
* rely on subjective completion definitions
* omit the Copilot Execution Instructions section

---

# 🧭 System Principle

Claude defines the work.
Copilot executes the work.
Tests validate the work.

The issue must be sufficient for execution without additional reasoning.
